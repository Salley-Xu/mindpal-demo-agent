# 长期记忆模块 v2.0 重构设计方案（更新版）

> **项目**：MindPal Pro 后端 v3.2 → v4.0 记忆系统重构  
> **文档版本**：v2.0 更新版  
> **日期**：2026-07-06  
> **设计定位**：基于当前 v2.0 Phase 0-1 已落地能力，设计 Phase 2-4 的完整 Memory System 演进方案  
> **核心目标**：将当前“风险记忆独立表 + MemoryStore 基础版”升级为“统一写入、语义检索、预算注入、生命周期管理、可评估”的长期记忆系统

---

## 1. 背景与设计出发点

当前 v2.0 已经完成两个关键工程升级：

1. **风险记忆独立表落地。**  
   风险记忆已经从 `user_profile.preferences.risk_memory` JSON blob 中拆出，迁移到 `risk_events` / `risk_baselines` / `risk_triggers` / `protective_factors`。风险事件采用 append-only 写入，baseline 更新进入单事务，解决了旧版本的并发覆盖问题。

2. **统一记忆存储基础设施落地。**  
   系统已经新增 `memory_items`、`memory_embeddings` 和 `memory_outbox`，并引入 `MemoryStore` 基础接口，为后续统一记忆写入、向量检索和异步合并打下基础。

但是，当前系统仍处于“v2.0 中间态”：

```text
风险记忆已经安全化
MemoryStore 已经建立
但 Memory Pipeline 尚未闭环
```

因此，本方案不再重复设计“从 0 到 1 的 v2.0”，而是面向已经更新后的系统，设计后续 Phase 2-4 的落地方案。

---

## 2. 设计目标

### 2.1 功能目标

| 目标 | 说明 |
|---|---|
| 统一写入 | 将情绪事件、压力源、偏好、推荐反馈、会话摘要等可长期复用信息统一进入 `memory_items` |
| 语义检索 | 在关键词匹配之外，引入 embedding 检索，支持语义相似记忆召回 |
| 多路融合 | 使用 BM25 / SQL 过滤 / 向量召回 / 风险优先级进行融合排序 |
| 预算注入 | 长期记忆注入 prompt 时必须遵守 token budget |
| 生命周期管理 | 不同 memory_type 具有不同 TTL、decay、archive、consolidation 策略 |
| 风险安全优先 | 保留独立 RiskMemoryStore，风险记忆不被普通记忆机制覆盖 |
| 可观测评估 | 记录召回、注入、使用、忽略、过期等日志，支持离线评估 |

---

### 2.2 非目标

本阶段不做以下事情：

1. 不把所有历史对话都向量化后无差别塞进长期记忆；
2. 不用 LLM 对每轮对话都生成复杂长期总结，避免成本和延迟过高；
3. 不取消 `risk_events` 等风险独立表，风险记忆继续作为专门安全子系统；
4. 不直接替换现有 `user_profile`，而是逐步引入 evidence-based profile 更新；
5. 不在 Phase 2 强制启用 embedding，可通过配置灰度开启。

---

## 3. 目标架构

### 3.1 总体架构

```text
用户输入 / 当前轮分析结果
  ↓
MemoryGateway
  ├── MemoryReadPipeline
  │   ├── QueryBuilder
  │   ├── MemoryRetriever
  │   │   ├── SQL / BM25 Retriever
  │   │   ├── Vector Retriever
  │   │   └── Risk Memory Reader
  │   ├── MemoryRanker
  │   └── MemoryInjector
  │
  └── MemoryWritePipeline
      ├── MemoryCandidateExtractor
      ├── MemoryPolicy
      ├── MemoryNormalizer
      ├── MemoryStore
      ├── RiskMemoryStore
      └── MemoryOutbox
```

---

### 3.2 模块职责

| 模块 | 职责 |
|---|---|
| `MemoryGateway` | 长期记忆系统统一入口，对 AgentOrchestrator 屏蔽底层表结构 |
| `MemoryCandidateExtractor` | 从当前轮输入、情绪分析、风险分析、推荐反馈中抽取候选记忆 |
| `MemoryPolicy` | 判断候选记忆是否值得写入，分配 importance、confidence、TTL |
| `MemoryNormalizer` | 标准化 memory_type、tags、summary、source_text、metadata |
| `MemoryStore` | 管理 `memory_items` 的 CRUD、upsert、状态更新 |
| `RiskMemoryStore` | 管理风险事件、基线、触发词、保护因素，保持独立安全语义 |
| `MemoryOutbox` | 管理 embedding、合并、归档等异步任务 |
| `MemoryRetriever` | 从 `memory_items`、`memory_embeddings` 和风险表中召回相关记忆 |
| `MemoryRanker` | 对候选记忆进行 RRF 融合和多因子重排 |
| `MemoryInjector` | 在 token budget 内选择和格式化最终注入内容 |
| `MemoryEvaluator` | 记录召回/注入日志，计算离线评估指标 |

## 4. 数据模型设计

### 4.1 `memory_items`：统一长期记忆主表

当前 v2.0 已经新增 `memory_items`。后续建议将其作为普通长期记忆主表。

建议字段如下：

```sql
CREATE TABLE IF NOT EXISTS memory_items (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    session_id TEXT,
    turn_id TEXT,

    memory_type TEXT NOT NULL,
    content TEXT NOT NULL,
    summary TEXT,
    source_text TEXT,

    importance REAL DEFAULT 0.5,
    confidence REAL DEFAULT 0.5,
    salience REAL DEFAULT 0.5,

    emotion TEXT,
    emotion_intensity REAL,
    risk_level TEXT,

    tags TEXT,
    metadata TEXT,

    status TEXT DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_accessed_at TIMESTAMP,
    expires_at TIMESTAMP,

    evidence_count INTEGER DEFAULT 1,
    supersedes_id TEXT,

    FOREIGN KEY (supersedes_id) REFERENCES memory_items(id)
);
```

---

### 4.2 memory_type 设计

| memory_type | 含义 | 示例 | 默认 TTL | 是否可注入 |
|---|---|---|---:|---|
| `stress_source` | 稳定压力源 | 用户长期受求职压力影响 | 180 天 | 是 |
| `support_preference` | 支持风格偏好 | 用户偏好直接可执行建议 | 长期 | 是 |
| `avoid_preference` | 回避风格 | 用户不喜欢空泛安慰 | 长期 | 是 |
| `mood_event` | 情绪事件 | 用户因实验失败感到焦虑 | 90 天 | 条件注入 |
| `coping_strategy` | 有效应对方式 | 用户曾通过散步缓解焦虑 | 180 天 | 是 |
| `recommendation_feedback` | 推荐反馈 | 用户拒绝冥想类内容 | 180 天 | 是 |
| `conversation_summary` | 会话摘要 | 本次会话主要围绕求职压力 | 180 天 | 条件注入 |
| `personal_fact` | 普通事实 | 用户正在准备算法岗面试 | 180 天或长期 | 条件注入 |
| `risk_shadow` | 风险事件摘要副本 | 风险系统中的可检索摘要 | 30 天 | 仅安全路径 |

说明：

- 真正的风险事实仍以 `risk_events` 为准；
- `risk_shadow` 只作为统一检索时的摘要副本，不作为安全判断来源；
- `support_preference` 和 `avoid_preference` 可以同步更新 `user_profile.preferences`，但长期应以 evidence-based memory 为来源。

---

### 4.3 `memory_embeddings`

```sql
CREATE TABLE IF NOT EXISTS memory_embeddings (
    memory_id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    model_name TEXT NOT NULL,
    embedding BLOB NOT NULL,
    dimension INTEGER NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY(memory_id) REFERENCES memory_items(id) ON DELETE CASCADE
);
```

embedding 生成不应阻塞主对话流程，应由 `memory_outbox` 异步完成。

---

### 4.4 `memory_outbox`

```sql
CREATE TABLE IF NOT EXISTS memory_outbox (
    id TEXT PRIMARY KEY,
    task_type TEXT NOT NULL,
    payload TEXT NOT NULL,
    status TEXT DEFAULT 'pending',
    retry_count INTEGER DEFAULT 0,
    last_error TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

任务类型建议：

| task_type | 说明 |
|---|---|
| `generate_embedding` | 为新 memory_item 生成向量 |
| `consolidate_memory` | 合并重复或相似记忆 |
| `decay_memory` | 执行衰减与归档 |
| `refresh_profile` | 基于 memory_items 重算用户画像字段 |
| `summarize_session` | 会话结束后生成长期摘要 |

---

### 4.5 `memory_access_logs`

建议新增访问日志表，用于评估召回和注入效果。

```sql
CREATE TABLE IF NOT EXISTS memory_access_logs (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    session_id TEXT,
    turn_id TEXT,
    memory_id TEXT,

    action TEXT NOT NULL,
    score REAL,
    rank_position INTEGER,
    token_cost INTEGER,
    injected BOOLEAN DEFAULT 0,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

`action` 可取值：

```text
retrieved
reranked
injected
skipped_budget
skipped_stale
skipped_low_score
used_by_model
user_corrected
```

## 5. 写入 Pipeline 设计

### 5.1 当前问题

当前系统已有多个写入点：

```text
ConversationManager.add_interaction()
MoodTrackingTool.log_mood_event()
UserProfileTool.update_user_profile()
RiskMemoryWriter.update()
RecommendGate feedback logging
```

v2.0 后风险记忆写入已经安全化，但其他长期信息仍然缺少统一策略。

---

### 5.2 目标写入流程

```text
当前轮对话结束
  ↓
InteractionPersistenceService.persist_turn()
  ↓
数据库事务：写入 conversation_history / emotion_timeline / sessions / mood_events
  ↓
MemoryCandidateExtractor.extract()
  ↓
MemoryPolicy.filter_and_score()
  ↓
MemoryNormalizer.normalize()
  ↓
MemoryStore.upsert_many()
  ↓
RiskMemoryStore.update()  # 仅风险相关事件
  ↓
MemoryOutbox.enqueue(generate_embedding / consolidate_memory)
```

---

### 5.3 记忆候选抽取

输入：

```python
@dataclass
class TurnContext:
    user_id: str
    session_id: str
    turn_id: str
    user_input: str
    ai_response: str
    emotion_result: dict
    risk_result: dict
    recommendation_result: dict | None
    conversation_summary: dict
```

输出：

```python
@dataclass
class MemoryCandidate:
    memory_type: str
    content: str
    source_text: str
    tags: list[str]
    emotion: str | None
    risk_level: str | None
    confidence: float
    evidence: dict
```

候选记忆来源：

| 来源 | 候选类型 |
|---|---|
| stress_source | `stress_source` |
| support style explicit keyword | `support_preference` |
| avoid style explicit keyword | `avoid_preference` |
| high-intensity emotion event | `mood_event` |
| repeated planning / help-seeking intent | `support_preference` |
| recommendation accepted / rejected | `recommendation_feedback` |
| level ≥ 2 risk event | `risk_shadow` + RiskMemoryStore 写入 |
| session end summary | `conversation_summary` |

---

### 5.4 写入门控策略

```python
class MemoryPolicy:
    def should_write(self, candidate: MemoryCandidate, recent_context: dict) -> bool:
        if candidate.memory_type == "stress_source":
            return appears_at_least(candidate, window=6, count=2)

        if candidate.memory_type in {"support_preference", "avoid_preference"}:
            return candidate.confidence >= 0.75 or explicit_user_statement(candidate)

        if candidate.memory_type == "mood_event":
            return candidate.emotion_intensity >= 0.65 or candidate.risk_level >= "level_1"

        if candidate.memory_type == "recommendation_feedback":
            return True

        if candidate.memory_type == "risk_shadow":
            return candidate.risk_level >= "level_2"

        return candidate.confidence >= 0.6
```

---

### 5.5 importance / confidence / TTL 计算

#### importance

```text
importance =
  0.30 × emotion_intensity
+ 0.25 × risk_weight
+ 0.20 × repetition_score
+ 0.15 × explicitness_score
+ 0.10 × recency_score
```

#### confidence

```text
confidence =
  0.50 × extraction_confidence
+ 0.30 × repetition_evidence
+ 0.20 × explicitness_score
```

#### TTL

| memory_type | TTL |
|---|---:|
| `mood_event` | 90 天 |
| `stress_source` | 180 天 |
| `recommendation_feedback` | 180 天 |
| `conversation_summary` | 180 天 |
| `risk_shadow` | 30 天 |
| `support_preference` | 长期，但可被覆盖 |
| `avoid_preference` | 长期，但可被覆盖 |

---

### 5.6 upsert 与去重

对稳定画像类记忆，不建议无限新增，而应采用 upsert / evidence_count 增强：

```text
如果新 stress_source 与已有 stress_source 相似：
  evidence_count += 1
  confidence = min(1.0, confidence + 0.1)
  updated_at = now
  expires_at = now + TTL
否则：
  新建 memory_item
```

对事件类记忆，例如 mood_event 和 risk_shadow，默认 append-only，但可以后续做 consolidation。

## 6. 风险记忆设计

### 6.1 保留独立 RiskMemoryStore

风险记忆不应该完全并入普通 `memory_items`。原因：

1. 风险判断属于安全链路，不应被普通记忆合并或删除影响；
2. 风险事件需要 append-only 审计；
3. 风险 baseline 需要稳定、快速、可解释；
4. 风险触发词与保护因素具有独立衰减逻辑。

因此 v2.0 后续设计采用双层结构：

```text
RiskMemoryStore：安全事实源
memory_items.risk_shadow：可检索摘要副本
```

---

### 6.2 风险写入流程

```text
risk_result.level >= level_2
且 subject == self
  ↓
RiskMemoryStore.add_risk_event_with_baseline_update()
  ↓
写入 risk_events
  ↓
重算 risk_baselines
  ↓
更新 risk_triggers
  ↓
如果需要语义检索：写入 memory_items.risk_shadow
```

---

### 6.3 风险读取流程

```text
当前轮风险评估完成
  ↓
RiskMemoryReader.get_baseline(user_id)
  ↓
读取 risk_baselines
  ↓
读取 active risk_triggers
  ↓
读取 protective_factors
  ↓
返回 baseline 包
  ↓
SessionRiskAggregator 应用 Safety Gate
```

---

### 6.4 风险记忆与 prompt 注入

风险记忆注入应遵循最小必要原则。

不建议直接注入完整历史风险事件，而应注入压缩状态：

```text
长期风险基线：medium
常见触发因素：求职压力、实验失败
保护因素：愿意联系朋友、愿意寻求具体建议
最近高风险时间：2026-xx-xx
```

只有在当前输入与历史风险触发因素高度相关时，才注入 1 条经过摘要的相似风险经历。

## 7. 检索 Pipeline 设计

### 7.1 QueryBuilder

输入当前轮信息：

```text
user_input
current_emotion
risk_level
stress_source
user_intent
conversation_stage
```

生成多路检索 query：

```python
MemoryQuery(
    semantic_query="用户当前因为实验失败和导师进度压力感到焦虑，正在寻求具体建议",
    keyword_terms=["实验失败", "导师", "进度", "焦虑"],
    memory_types=["stress_source", "mood_event", "support_preference", "coping_strategy"],
    risk_level_filter=None,
    max_age_days=180,
)
```

---

### 7.2 多路召回

```text
QueryBuilder
  ↓
1. SQL filter recall
   - user_id
   - status = active
   - memory_type in allowed_types
   - expires_at > now

2. Keyword / BM25 recall
   - content
   - summary
   - tags

3. Vector recall
   - memory_embeddings cosine similarity

4. Safety recall
   - risk_baselines
   - risk_triggers
   - protective_factors
```

---

### 7.3 RRF 融合

RRF 公式：

```text
score(item) = Σ 1 / (k + rank_i)
```

其中 `k = MEMORY_RRF_K`，默认 60。

融合来源：

| 排名来源 | 权重 |
|---|---:|
| BM25 排名 | 1.0 |
| 向量相似度排名 | 1.2 |
| 最近访问 / 最近创建排名 | 0.6 |
| importance 排名 | 0.8 |
| 风险相关排名 | 1.5 |

---

### 7.4 多因子重排

最终排序分数：

```text
final_score =
  0.35 × semantic_similarity
+ 0.20 × keyword_score
+ 0.15 × importance
+ 0.10 × confidence
+ 0.10 × recency_score
+ 0.10 × safety_priority
- 0.15 × stale_penalty
```

特殊规则：

```text
如果当前 risk_level >= level_2：
    risk_shadow / protective_factor / support_preference 优先级提升

如果当前用户明确要求“不要提以前的事”：
    episodic memory 注入降权

如果 memory_item.status != active：
    不注入

如果 memory_item.confidence < 0.4：
    不注入
```

## 8. 注入 Pipeline 设计

### 8.1 Token Budget

使用配置：

```python
memory_budget = MAX_CONTEXT_TOKENS * MEMORY_INJECTION_BUDGET_RATIO
```

例如：

```text
MAX_CONTEXT_TOKENS = 2400
MEMORY_INJECTION_BUDGET_RATIO = 0.15
memory_budget = 360 tokens
```

---

### 8.2 注入优先级

| 优先级 | 类型 | 注入条件 |
|---:|---|---|
| 1 | risk baseline / active trigger | 每轮风险链路可用，但 prompt 中压缩展示 |
| 2 | support_preference / avoid_preference | 与回答风格相关时注入 |
| 3 | 当前主题相关 stress_source | 当前输入匹配时注入 |
| 4 | coping_strategy | 当前需要建议时注入 |
| 5 | recommendation_feedback | 当前触发推荐时注入 |
| 6 | mood_event / conversation_summary | 仅高度相关时注入 |

---

### 8.3 注入格式

建议格式：

```text
【相关长期记忆】
- 稳定偏好：用户更希望获得直接、可执行的建议，避免空泛安慰。
- 相关压力源：用户近期多次提到实验失败和课题进展压力。
- 历史有效策略：用户曾表示通过拆分任务和短期计划能缓解焦虑。
- 风险基线：medium；常见触发因素包括求职压力、实验失败。
```

避免格式：

```text
用户在 2026-xx-xx 说过：“......”
```

原因：过度暴露历史原文会让用户感到突兀，也会浪费 token。

---

### 8.4 注入去重

注入前需要去重：

```text
如果 support_preference 已在 user_profile 中出现，不再从 memory_items 重复注入
如果 stress_source 已在会话摘要中出现，不再重复注入长期压力源
如果 risk trigger 已在当前风险状态中出现，不再重复注入 risk_shadow
```

---

## 9. 生命周期管理

### 9.1 decay 策略

不同类型记忆使用不同衰减策略。

| 类型 | 衰减依据 | 动作 |
|---|---|---|
| mood_event | expires_at 到期 | status = archived |
| stress_source | 长期未被提及 | importance 下降，TTL 延长或归档 |
| recommendation_feedback | 超过 180 天 | 降低权重 |
| risk_event | 30 天 | decayed = true，但保留审计记录 |
| support_preference | 出现相反证据 | 新记忆 supersede 旧记忆 |
| conversation_summary | 会话长期无访问 | archive |

---

### 9.2 consolidation 策略

当用户多次表达相似信息时，不应无限新增。

示例：

```text
记忆 1：用户因实验失败感到焦虑
记忆 2：用户因课题推进不动感到压力
记忆 3：用户担心导师问实验进度
```

可合并为：

```text
用户长期存在科研进展相关压力，主要触发因素包括实验失败、课题推进缓慢和导师进度询问。
```

合并后：

```text
新建或更新 stress_source memory_item
原 mood_event 保留但降低注入优先级
metadata 中记录 evidence_ids
```

---

### 9.3 画像刷新

长期目标是让 `user_profile.preferences` 不再是唯一事实源，而是由 `memory_items` 计算得到。

```text
memory_items.active
  ↓
按 memory_type 聚合
  ↓
计算 main_stress_sources / preferred_support_style / avoid_style
  ↓
刷新 user_profile.preferences
```

这样可以解决画像字段缺少 evidence trail 的问题。

## 10. 事务与一致性设计

### 10.1 主交互写入事务

建议新增：

```python
class InteractionPersistenceService:
    async def persist_turn(self, turn: TurnContext) -> PersistResult:
        async with self.db.transaction() as tx:
            await tx.add_conversation_turn(...)
            await tx.add_emotion_event(...)
            await tx.update_session(...)
            await tx.add_mood_event(...)
            await tx.upsert_profile_delta(...)
            memory_candidates = self.extractor.extract(turn)
            memory_items = self.policy.filter_and_score(memory_candidates)
            await tx.upsert_memory_items(memory_items)
            await tx.enqueue_outbox_tasks(memory_items)
        return PersistResult(success=True)
```

---

### 10.2 Outbox 事务边界

主请求内只做必要写入。

```text
同步事务内：
- conversation_history
- sessions
- mood_events
- user_profile delta
- memory_items
- memory_outbox task
- risk_events / risk_baselines

异步 outbox：
- embedding 生成
- 相似记忆合并
- 过期记忆归档
- profile refresh
```

这样即使异步任务失败，也不会影响主对话历史和核心长期记忆。

---

### 10.3 幂等设计

每轮写入建议使用稳定 `turn_id`：

```text
turn_id = hash(user_id + session_id + turn_number + timestamp_bucket)
```

`memory_items` 可以用：

```text
memory_id = hash(user_id + memory_type + normalized_content)
```

对于事件型记忆，使用随机 UUID；对于画像型记忆，使用 deterministic key 便于 upsert。

## 13. 迁移路线

### Phase 2：统一写入与事务化

目标：完成 Memory Pipeline 写入侧闭环。

任务：

1. 新建 `memory_gateway.py`；
2. 新建 `memory_policy.py`；
3. 新建 `memory_candidate_extractor.py`；
4. 新建 `interaction_persistence_service.py`；
5. 将 `add_interaction()` 中多表写入收敛为单事务；
6. 将重要 `mood_events`、稳定压力源、支持偏好、推荐反馈写入 `memory_items`；
7. 保留旧读取逻辑作为 fallback；
8. 新增写入一致性测试。

验收标准：

```text
- 单轮交互写入失败时不会出现半写入状态
- 稳定压力源可以进入 memory_items
- 支持风格偏好可以进入 memory_items
- 风险事件仍优先进入 RiskMemoryStore
- 旧 prompt 构建逻辑不受破坏
```

---

### Phase 3：语义检索与预算化注入

目标：完成 Memory Pipeline 读取侧闭环。

任务：

1. 启用 `MEMORY_EMBEDDING_ENABLED` 灰度；
2. 实现 `MemoryEmbeddingService`；
3. 实现 `MemoryRetriever`；
4. 实现 BM25 / SQL + vector hybrid retrieval；
5. 实现 RRF 融合；
6. 实现 `MemoryRanker`；
7. 实现 `MemoryInjector`；
8. 将 `_build_relevant_memory_context()` 替换为 `memory_gateway.read_for_prompt()`；
9. 增加 token budget 测试。

验收标准：

```text
- 相同语义不同表述可以召回相关记忆
- 注入内容不超过 memory token budget
- 风险相关记忆优先级高于普通 mood_event
- 重复记忆不会多次注入
```

## 16. 灰度与回滚策略

### 16.1 配置开关

| 配置项 | 用途 |
|---|---|
| `MEMORY_ENABLED` | 总开关 |
| `MEMORY_EMBEDDING_ENABLED` | 是否启用向量检索 |
| `MEMORY_WRITE_TO_ITEMS_ENABLED` | 是否写入 `memory_items` |
| `MEMORY_READ_FROM_ITEMS_ENABLED` | 是否从 `memory_items` 读取 |
| `MEMORY_RISK_SHADOW_ENABLED` | 是否同步 risk_shadow |
| `MEMORY_INJECTION_ENABLED` | 是否注入长期记忆 |

---

### 16.2 回滚路径

```text
如果 memory_items 写入异常：
  关闭 MEMORY_WRITE_TO_ITEMS_ENABLED
  保留旧 user_profile / mood_events / risk_events 路径

如果语义检索异常：
  关闭 MEMORY_EMBEDDING_ENABLED
  回退关键词检索

如果注入导致回复变差：
  关闭 MEMORY_INJECTION_ENABLED
  保留风险 baseline 读取
```

风险记忆独立表不建议回滚到 JSON blob，只保留 JSON fallback 读取兼容旧数据。

## 17. 推荐落地顺序

优先级建议如下：

```text
1. 先做 InteractionPersistenceService，解决主写入链路事务问题
2. 再让重要长期信息进入 memory_items
3. 然后启用 memory_outbox 生成 embedding
4. 再做 hybrid retrieval + RRF
5. 最后做 MemoryInjector token budget 和生命周期管理
```

不要一开始就做复杂的 LLM 记忆摘要。当前更关键的是工程闭环：

```text
写得准 → 查得到 → 排得对 → 注入少而有用 → 能评估
```

## 18. 最终目标形态

完成 Phase 2-4 后，长期记忆系统应达到如下形态：

```text
短时记忆：ConversationManager 管理当前会话上下文和 token 压缩
长期普通记忆：MemoryStore 管理 memory_items、embedding、TTL、合并
长期安全记忆：RiskMemoryStore 管理 risk_events、baseline、trigger、protective factor
读取链路：MemoryRetriever + MemoryRanker 召回并排序相关记忆
注入链路：MemoryInjector 在 token budget 内格式化注入
写入链路：MemoryPolicy 控制候选记忆是否写入
评估链路：MemoryEvaluator 记录和评估记忆效果
```

这时，长期记忆模块才真正完成从“持久化数据”到“Agent Memory System”的升级。

## 19. 总结

v2.0 当前已经完成最关键的安全性重构：风险记忆独立表和事务写入已经落地，`MemoryStore` 与 `memory_items` 也已经建立基础。因此，后续设计重点不再是“要不要重构”，而是如何把已建立的基础设施真正接入完整记忆链路。

后续核心路线是：

```text
Phase 2：统一写入 + 主链路事务化
Phase 3：语义检索 + RRF 融合 + token budget 注入
Phase 4：生命周期管理 + 记忆合并 + 质量评估
```

最终目标是让长期记忆系统具备五个能力：

```text
可控写入
可靠存储
相关召回
克制注入
持续评估
```

只有做到这五点，长期记忆才不会只是“存了很多历史”，而是真正成为 Agent 个性化、连续性和安全性的基础设施。
