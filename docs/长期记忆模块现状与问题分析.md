# 长期记忆模块现状与问题分析（v2.0 更新版）

> **项目**：MindPal Pro 后端 v3.2 → v4.0 记忆系统重构  
> **文档版本**：v2.0 更新版  
> **日期**：2026-07-06  
> **依据文档**：《长期记忆模块 — 技术现状文档 v2.0》  
> **范围**：对当前长期记忆模块的架构现状、已完成重构、剩余问题和后续演进方向进行系统化分析

---

## 1. 总体结论

经过 Phase 0-1 重构后，MindPal Pro 的长期记忆系统已经从早期的“分散式持久化能力”进入到“记忆系统架构化重构中期”。

当前系统已经完成两个关键升级：

1. **风险记忆从 `user_profile.preferences` JSON blob 中拆出，迁移为独立风险记忆表。**  
   这解决了旧版本中最严重的 P0 问题：并发请求下风险事件可能互相覆盖。

2. **引入了统一记忆存储雏形：`memory_items` 表 + `MemoryStore` 接口。**  
   这说明系统已经开始从“多个业务模块各自存储长期信息”，转向“以统一 Memory 层承载跨会话记忆”。

因此，当前长期记忆模块的定位可以概括为：

> v2.0 已经完成风险记忆安全重构，并建立统一记忆存储基础设施；但完整的 Memory Pipeline 尚未闭环，语义检索、统一写入策略、注入预算、记忆衰减与合并机制仍处在待完善阶段。

## 2. v2.0 相比旧版的核心变化

| 维度 | v1.x 状态 | v2.0 当前状态 | 影响 |
|---|---|---|---|
| 风险记忆存储 | 存在 `user_profile.preferences.risk_memory` JSON blob 中 | 拆分为 `risk_events` / `risk_baselines` / `risk_triggers` / `protective_factors` 独立表 | 解决并发覆盖风险 |
| 风险事件写入 | 先读 JSON、修改、整体写回 | `risk_events` append-only + baseline 单事务更新 | 写入更安全，可审计 |
| 风险基线 | 嵌套在 JSON 中，重算依赖画像字段 | `risk_baselines` 每用户一行 | 读取路径清晰，适合作为 Safety Gate 输入 |
| 触发词统计 | 存在 JSON 数组中 | `risk_triggers` 独立统计，支持 ON CONFLICT UPDATE | 方便频次统计与衰减 |
| 保护因素 | JSON 字段 | `protective_factors` 独立表 | 更利于结构化维护 |
| 统一记忆表 | 无 | 新增 `memory_items` | 为后续语义检索和生命周期管理打基础 |
| 向量存储 | 无 | 新增 `memory_embeddings`，但默认未启用 | 为 Phase 3 做准备 |
| 异步任务队列 | 无 | 新增 `memory_outbox` | 为 embedding / consolidation 异步化做准备 |
| 风险审计 | 当前风险是否被基线影响不明显 | `baseline_applied` 审计字段 | 便于调试 Safety Gate |
| 测试覆盖 | 有风险记忆测试 | 新增并发写入测试 `test_p0_risk_concurrency.py` | 可验证 P0 修复 |

## 3. 当前长期记忆系统架构现状

### 3.1 当前系统边界

当前长期记忆系统由以下几类存储共同组成：

```text
长期记忆系统
├── 会话历史记忆
│   ├── sessions
│   ├── conversation_history
│   └── emotion_timeline
│
├── 用户画像记忆
│   └── user_profile.preferences
│
├── 情绪事件记忆
│   └── mood_events
│
├── 风险安全记忆 v2.0
│   ├── risk_events
│   ├── risk_baselines
│   ├── risk_triggers
│   └── protective_factors
│
├── 统一长期记忆 v2.0 基础表
│   ├── memory_items
│   ├── memory_embeddings
│   └── memory_outbox
│
└── 推荐反馈记忆
    ├── recommendation_events
    └── recommendation_feedback
```

从结构上看，系统已经不再是单纯的 SQLite 会话持久化，而是开始向专门的 Memory System 演进。

---

### 3.2 当前数据流

当前每轮对话的记忆数据流可以拆成两条链路：

#### 读取链路

```text
用户输入
  ↓
AgentOrchestrator.run_agent()
  ↓
ConversationManager.get_or_create_session_async()
  ↓
读取当前会话历史 / 上下文摘要
  ↓
UserProfileTool.get_profile()
  ↓
读取 user_profile.preferences
  ↓
RiskMemoryReader.get_baseline()
  ↓
读取 risk_baselines + risk_triggers + protective_factors
  ↓
MoodTrackingTool.get_recent_trend()
  ↓
读取 mood_events
  ↓
_build_initial_messages()
  ↓
将会话摘要、压缩上下文、用户画像、相关长期记忆、风险状态注入 prompt
```

#### 写入链路

```text
Agent 输出完成
  ↓
ConversationManager.add_interaction()
  ↓
写入内存 session.history
  ↓
_schedule_persistence()
  ↓
异步写入 conversation_history / emotion_timeline / sessions / mood_events
  ↓
_update_long_term_signals()
  ↓
更新 user_profile.preferences
  ↓
RiskMemoryWriter.update()
  ↓
risk_memory_store.add_risk_event_with_baseline_update()
  ↓
写入 risk_events，并在同一事务中更新 risk_baselines
```

## 4. 已完成能力分析

### 4.1 风险记忆独立表：v2.0 最重要的正确性修复

旧版本最大风险是 `risk_memory` 存储在用户画像 JSON 中。由于 JSON blob 需要整体读取、修改、写回，在并发请求下非常容易出现覆盖写。

v2.0 将风险记忆拆分为四张独立表：

| 表名 | 职责 | 设计价值 |
|---|---|---|
| `risk_events` | 存储 append-only 风险事件 | 保证风险事件不被覆盖，便于审计 |
| `risk_baselines` | 存储每用户当前风险基线 | 便于 Safety Gate 快速读取 |
| `risk_triggers` | 存储高频风险触发因素 | 便于跨会话识别风险模式 |
| `protective_factors` | 存储保护因素 | 支持更稳健的干预策略 |

尤其是 `risk_events` 采用 append-only 设计，这是风险安全系统中非常合理的做法：

```text
风险事件不应该被覆盖，只应该新增、衰减或归档。
```

这使风险记忆从“画像字段”升级成了“可追踪的安全事件日志”。

---

### 4.2 风险基线单事务更新

v2.0 中 `add_risk_event_with_baseline_update()` 将风险事件写入和 baseline 更新放进同一个事务：

```sql
BEGIN TRANSACTION;
  INSERT INTO risk_events (...);
  SELECT * FROM risk_events WHERE user_id=? AND decayed=0;
  INSERT OR REPLACE INTO risk_baselines (...);
COMMIT;
```

这带来两个好处：

1. **风险事件不会丢失。**  
   并发写入时，SQLite 会串行化写事务，避免旧版 JSON blob 的 lost update。

2. **baseline 与事件日志更一致。**  
   写入新事件后立即重算 baseline，可以减少“事件已写入但基线未更新”的不一致状态。

---

### 4.3 `baseline_applied` 审计字段

SessionRiskAggregator 的 Safety Gate 会用长期风险基线影响当前轮风险判断：

```text
baseline = high 且 session_level < level_1 → 提升至 level_1
baseline = medium 且 当前轮和上轮不都是 level_0 → 提升至 level_1
```

v2.0 新增 `baseline_applied` 字段后，可以明确知道当前风险等级是否受长期基线影响。

这对风险系统非常重要，因为它解决了一个调试问题：

> 当前轮被判成 level_1，到底是因为当前输入本身有风险，还是因为长期风险基线导致保守升级？

有了该字段，后续可以更准确地评估 Safety Gate 是否过度敏感。

---

### 4.4 `MemoryStore` 与 `memory_items` 打下统一记忆基础

v2.0 新增 `memory_items`，说明系统开始从多个业务表向统一 Memory Store 过渡。

理想情况下，未来所有可长期复用的信息都可以抽象为 `MemoryItem`：

```text
MemoryItem
├── memory_type        记忆类型
├── content            记忆内容
├── summary            记忆摘要
├── source_text         原始来源
├── importance         重要性
├── confidence         置信度
├── emotion            情绪标签
├── risk_level         风险等级
├── tags               标签
├── created_at         创建时间
├── updated_at         更新时间
├── last_accessed_at   最近访问时间
├── expires_at         过期时间
└── status             active / archived / decayed
```

这是后续引入语义检索、记忆衰减、记忆合并、注入预算控制的基础。

---

### 4.5 配置项开始系统化

v2.0 新增了多项 Memory System 配置，例如：

| 配置项 | 作用 |
|---|---|
| `MEMORY_ENABLED` | 控制是否启用 v2.0 记忆系统 |
| `MEMORY_EMBEDDING_ENABLED` | 控制是否启用 embedding 生成 |
| `MEMORY_INJECTION_BUDGET_RATIO` | 控制长期记忆占上下文 token 的比例 |
| `MEMORY_MAX_ITEMS_PER_USER` | 控制每用户最大记忆条目 |
| `MEMORY_RRF_K` | 为后续 RRF 融合排序预留 |
| `MEMORY_DECAY_DAYS_*` | 控制不同记忆类型的 TTL |

这说明后续记忆系统已经开始向“可配置、可灰度、可评估”的方向演进。

## 5. 当前仍然存在的问题

### 5.1 P0：`add_interaction()` 主写入链路仍缺少事务原子性

虽然风险记忆写入已经事务化，但主会话写入链路仍然存在原子性问题。

当前 `add_interaction()` 会异步写入：

```text
1. conversation_history
2. emotion_timeline
3. sessions
4. mood_events
5. user_profile
```

如果这些写入是多个独立 Task 或多个独立事务，那么会出现以下不一致：

| 失败位置 | 可能结果 |
|---|---|
| `conversation_history` 成功，`mood_events` 失败 | 对话存在，但情绪趋势缺失 |
| `mood_events` 成功，`sessions` 更新失败 | 情绪事件存在，但会话活跃时间不准确 |
| `user_profile` 成功，历史写入失败 | 画像更新缺少可追溯来源 |
| 部分异步 Task 被取消 | 内存状态和数据库状态不一致 |

这不是风险记忆独有问题，而是整个长期记忆写入链路的一致性问题。

**建议：**

将每轮交互的核心持久化操作封装成统一事务：

```python
async with db.transaction():
    await add_conversation_turn(...)
    await add_emotion_event(...)
    await update_session(...)
    await add_mood_event(...)
    await upsert_profile_delta(...)
```

对于 embedding、记忆合并、统计类更新，可以通过 `memory_outbox` 异步执行。

---

### 5.2 P1：统一记忆表已建立，但统一写入 Pipeline 尚未形成

当前虽然有 `memory_items` 和 `MemoryStore`，但从现状看，系统仍然主要依赖原有路径：

```text
mood_events → 情绪趋势
user_profile.preferences → 用户画像
risk_events → 风险记忆
recommendation_feedback → 推荐反馈
```

也就是说，`memory_items` 目前更像“基础设施”，还没有成为长期记忆的主入口。

真正的统一记忆系统应该有一条明确写入链路：

```text
当前轮对话
  ↓
MemoryCandidateExtractor
  ↓
MemoryPolicy.should_write()
  ↓
MemoryNormalizer
  ↓
MemoryStore.upsert()
  ↓
Outbox: embedding / consolidation / decay
```

否则长期记忆仍然会继续分散在 14 张表中，只是比旧版多了一张 `memory_items`。

---

### 5.3 P1：长期记忆检索仍以关键词匹配为主

当前“相关长期记忆”注入主要依赖：

```text
焦点词提取
压力源匹配
事件摘要/片段关键词匹配
情绪相似度加分
高风险事件加分
```

这种方式在小规模演示中可用，但在真实长期使用中会遇到明显瓶颈。

例如以下三句话语义接近，但关键词可能不同：

```text
“我最近实验一直失败”
“课题推进不动”
“导师问进度我很焦虑”
```

如果只依赖关键词，系统很难稳定召回同一类“科研压力 / 实验失败 / 导师压力”记忆。

**建议：**

在 Phase 3 中引入 hybrid retrieval：

```text
当前输入 + 情绪状态 + 风险状态
  ↓
生成 memory query
  ↓
BM25 / SQL 关键词召回
  ↓
向量召回
  ↓
RRF 融合
  ↓
多因子重排
  ↓
Token budget 内注入
```

---

### 5.4 P1：记忆注入还没有真正受 Token Budget 控制

虽然配置中已经有 `MEMORY_INJECTION_BUDGET_RATIO`，但现状中 `_build_relevant_memory_context()` 对 mood event 的注入仍然没有严格检查 token 消耗。

长期看，这会造成两个问题：

1. **上下文挤占。**  
   长期记忆过多时，会挤压当前对话上下文和安全指令。

2. **注入不稳定。**  
   不同轮次注入内容长度差异过大，会影响模型输出稳定性。

建议将 prompt 构建分成固定预算：

| Prompt 区域 | 建议预算 |
|---|---:|
| 系统基础指令 | 25% |
| 当前会话上下文 | 40% |
| 长期记忆注入 | 15% |
| 风险/情绪状态 | 10% |
| 工具与推荐状态 | 10% |

长期记忆内部再按优先级分配：

```text
风险相关记忆 > 稳定偏好 > 当前主题相关经历 > 推荐反馈 > 低重要性情绪事件
```

---

### 5.5 P2：短时记忆、长期画像和统一记忆边界仍然不够清晰

当前系统中存在几类相近信息：

| 信息 | 当前存储位置 | 问题 |
|---|---|---|
| 当前会话历史 | `session.history` / `conversation_history` | 属于短时或会话记忆 |
| 长期压力源 | `user_profile.preferences.main_stress_sources` | 属于稳定画像 |
| 情绪事件 | `mood_events` | 属于时间序列记忆 |
| 风险事件 | `risk_events` | 属于安全记忆 |
| 通用记忆 | `memory_items` | 尚未成为主入口 |

问题不在于表多，而在于缺少清晰的层级关系。

建议明确四层：

```text
Working Memory       当前轮和当前窗口
Session Memory       当前会话摘要与阶段状态
Episodic Memory      跨会话事件、情绪、经历
Semantic/Profile Memory  稳定偏好、压力源、支持风格
Safety Memory        风险事件、基线、触发词、保护因素
```

这样可以避免所有东西都被笼统叫作“长期记忆”。

---

### 5.6 P2：`mood_events` 和部分画像字段仍缺少生命周期管理

风险事件已经有 30 天衰减，但 `mood_events` 和 `user_profile` 仍然可能无限增长。

这会带来三个问题：

1. 历史情绪事件越来越多，检索成本上升；
2. 很久以前的压力源可能不再代表当前用户状态；
3. 长期画像可能过时，但系统缺少主动修正机制。

建议为不同记忆类型设计不同生命周期：

| 记忆类型 | 默认 TTL | 衰减策略 |
|---|---:|---|
| 普通 mood_event | 90 天 | 过期归档 |
| stress_source | 180 天 | 长期未出现则降低权重 |
| preferred_support_style | 无固定 TTL | 被新证据覆盖 |
| recommendation_feedback | 180 天 | 近期反馈权重更高 |
| risk_event | 30 天 | 已有 decayed 标记 |
| protective_factor | 无固定 TTL | 定期确认 |

---

### 5.7 P3：上下文压缩仍是规则截断，不是真正摘要记忆

当前 token-aware compression 采用规则：近期原文保留，较早轮次转为片段式摘要。

优点是低成本、确定性强；缺点是：

- 对长期目标、关键转折、用户承诺等信息保留不足；
- 压缩结果缺少结构化字段；
- 无法作为高质量 session summary 进入长期记忆。

后续可以引入轻量 LLM 摘要，但不建议一开始完全替换规则压缩。更合理的方式是：

```text
规则压缩负责实时上下文窗口控制
LLM 摘要负责会话结束后的长期摘要固化
```

## 7. 根因分析

当前剩余问题可以归结为三个根因。

### 7.1 仍然是“多模块记忆”，不是“统一记忆流水线”

虽然 v2.0 引入了 `memory_items`，但业务模块仍然各自负责写入：

```text
ConversationManager 写会话历史
MoodTrackingTool 写情绪事件
UserProfileTool 写用户画像
RiskMemoryWriter 写风险记忆
RecommendGate 写推荐反馈
```

这会导致：

- 写入标准不统一；
- importance / confidence 不统一；
- TTL 不统一；
- 检索和注入无法统一排序；
- 后续维护成本继续上升。

---

### 7.2 记忆读取仍然偏“字段查询”，不是“上下文相关检索”

当前系统读取长期记忆的方式仍然偏固定：

```text
读取 profile
读取 baseline
读取 recent mood events
读取 recommendation feedback
```

但真正的 Agent 长期记忆应该根据当前输入动态召回：

```text
当前用户在谈什么？
当前情绪是什么？
当前风险是什么？
哪些历史记忆对当前回答有帮助？
哪些记忆虽然相关但不应该注入？
```

这需要 MemoryRetriever 和 MemoryInjector 两层明确分工。

---

### 7.3 缺少记忆质量评估闭环

目前测试主要覆盖功能正确性，例如：

- 是否写入；
- 是否衰减；
- 是否并发安全；
- prompt 是否包含记忆上下文。

但还缺少记忆系统的质量评估，例如：

| 指标 | 含义 |
|---|---|
| Recall@K | 当前输入下是否召回了应该召回的历史记忆 |
| Precision@K | 注入的记忆是否真正相关 |
| Injection Utility | 注入记忆是否改善回答质量 |
| Safety False Escalation Rate | 长期风险基线是否导致过度升级 |
| Stale Memory Rate | 注入内容是否过时 |
| User Correction Rate | 用户纠正系统记忆的频率 |

没有这些指标，系统很难判断“记忆越来越多”到底是在增强 Agent，还是在污染上下文。

## 9. 当前版本适合怎么对外描述

可以在项目文档或面试中这样描述：

> 长期记忆模块最初是基于 SQLite 的跨会话持久化机制，包含会话历史、用户画像、情绪事件、推荐反馈和风险记忆。v2.0 重构后，我将风险记忆从用户画像 JSON 中拆分为独立的 `risk_events`、`risk_baselines`、`risk_triggers` 和 `protective_factors` 表，并采用 append-only 风险事件日志和单事务 baseline 更新，解决了并发请求下风险记忆覆盖的问题。同时引入 `memory_items` 与 `MemoryStore` 作为统一记忆存储基础，为后续语义检索、记忆衰减、记忆合并和 token budget 注入做准备。当前剩余重点是将各业务模块的记忆写入统一到 Memory Pipeline，并引入 BM25 + 向量召回 + RRF 融合的相关记忆检索机制。

## 10. 总结

v2.0 的长期记忆模块已经完成了最关键的安全性重构：风险记忆从 JSON blob 中拆出，并通过独立表和事务写入解决并发覆盖问题。同时，`memory_items` 和 `MemoryStore` 的引入说明系统已经开始从业务表持久化走向统一 Memory System。

但当前版本仍处于中间态：

```text
已完成：风险记忆安全化 + 统一记忆表基础设施
未完成：统一写入 pipeline + 语义检索 + 注入预算 + 生命周期管理 + 质量评估
```

因此，下一阶段的核心不应该继续增加零散记忆字段，而是要完成 Memory System 的闭环：

```text
记忆候选提取 → 写入门控 → 统一存储 → 语义检索 → 多因子重排 → 预算化注入 → 衰减合并 → 质量评估
```
